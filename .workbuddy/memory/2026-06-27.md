## 修复：首页排序切换导致 APP 卡死
- **根因**：`PhotosViewModel.baseFilteredList` 的 `combine` 中包含了 `_currentSortType` 作为依赖，但 lambda 内根本没用它。切换排序时 `baseFilteredList` 不必要地重跑全量过滤（`withContext(Dispatchers.Default)`），与 `photoListFlow` 的排序/分组计算抢占线程池，大量照片时导致阻塞。
- **修复**：从 `baseFilteredList` 的 combine 中移除 `_currentSortType` 参数（第 344 行原为 `_currentSortType,`）。排序只应在 `photoListFlow` 的 combine 中触发。
- **影响范围**：只改一行，不影响其他功能。AlbumDetailViewModel 无类似问题。

## 修复：排序切换时 Room CursorWindow 崩溃（第二次修复）
- **根因**：`photoDao.getAllPhotosFlow()` 通过 `stateIn(WhileSubscribed(5000))` 收集。切换排序时 `photoListFlow` recompute 期间 subscriber 短暂掉到 0，`WhileSubscribed` 取消上游 Flow 集合，Room 的 `createFlow` 被取消时 CursorWindow 处于无效状态，触发 `Couldn't read row X, col 0 from CursorWindow`。
- **修复**：将 `getAllPhotosFlow()` 提取为独立的 `rawPhotoEntities` StateFlow，使用 `SharingStarted.Lazily`（首订启动后不取消），`baseFilteredList` 改为从 `rawPhotoEntities` 读取。Room Flow 不再受 `WhileSubscribed` 取消影响。
- **改动**：`PhotosViewModel.kt` 新增 `rawPhotoEntities` 行 343-345，`baseFilteredList` 的 combine 改用 `rawPhotoEntities` 替代 `photoDao.getAllPhotosFlow()`。

## 最终修复：放弃 Room.Flow，改用 suspend 定时刷新（第五次修复）
- **根因确认**：之前的 `retry` 无限重试在 `Dispatchers.Main.immediate` 上疯狂循环，导致 `MessageQueue` 被占满。`Looper` 不断处理 `retry` 的消息，无法处理用户输入和 UI 更新 → 主线程卡死（ANR）→ 系统杀进程/用户点击关闭 → "闪退"。
- **为什么切换分组不崩**：分组切换不触发 `rawPhotoEntities` 的 `retry` 循环。`retry` 循环是独立运行的。用户感知到的"崩溃时刻"是切换排序时，因为此时主线程在访问 StateFlow value，恰好踩中了 retry 循环的高峰期。
- **修复**：彻底放弃 `Room.Flow`（`getAllPhotosFlow()`），改用 `suspend fun getAllPhotos()` 手动定时刷新。
  - `getAllPhotos()` 是 suspend 函数，一次性返回 `List<PhotoEntity>`，不持有 cursor，不受 `InvalidationTracker` 影响，`IllegalStateException` 根本不会发生。
  - 每 2 秒从 `Dispatchers.IO` 拉取一次全量数据，彻底规避 cursor 竞态。
  - 监听 `mediaScanner.isExtractingExifFlow`，EXIF 提取完成后立即刷新，避免等待 2 秒定时器。
- **改动**：
  - `PhotosViewModel.kt`：移除 `retry` import；移除 `rawPhotoEntities` 的 Flow 收集；添加 `_rawPhotoEntities` MutableStateFlow；`init` 块添加定时刷新协程和 EXIF 提取监听；`baseFilteredList` 的 combine 改用 `_rawPhotoEntities`。
  - `MediaScanner.kt`：修复 `performIncrementalScan` 与 `syncSpecificPhotos` 的 Mutex 死锁（移除 `syncSpecificPhotos` 的 Mutex 包裹）。

## minSdk 提升改造方案（docs/minsdk35-migration-plan.md）

用户提出将 minSdk 30 → Android 15 以获取 AVIF/HEIF/JXL 原生支持。经源码走查（15 处 SDK_INT 分支、7 个文件）与官方文档核实：

- **关键事实修正**：JXL 永无 Android 原生支持（官方媒体格式表无此格式），必须保留 jxl-coder；AVIF 解码 API 34 起强制原生，10-bit/HDR 显示（hasGainmap、COLOR_MODE_HDR）也是 API 34；API 35 仅多 ISO 21496-1 gain map（Ultra HDR 1.1）与 HDR headroom。
- **决策建议**：推荐 minSdk 34（覆盖 54.5%，分支可清零，未来升 35 只改一个数字）；minSdk 35 覆盖 41% 可选。
- **紧急项**：Play 要求 2026-08-31 起 targetSdk ≥ 36，项目现为 35，需先升级。
- **改造要点**：移除 avif-coder（AVIF/HEIF 走原生）、AvifRegionDecoder 重构为 ImageDecoder、权限三档合并（建议去掉 READ_MEDIA_VISUAL_USER_SELECTED 避免部分授权降级）、移除 READ_EXTERNAL_STORAGE、desugar/splashscreen 可评估移除。
- 交付：完整分阶段方案文档（6 阶段 + commit 拆分 + 回归矩阵 + 风险表）。

后续若执行改造，按方案中的 commit 拆分逐个落地，每个 commit 可独立回退。

## minSdk 决策定稿（v2，同日下午）

- 用户拍板：**minSdk = 35（Android 15）**，JXL 单独走 jxl-coder，其余格式全走系统原生解码，HDR 效果必须正确保留。
- 走查发现 3 个 P0 级 HDR 缺陷（已写入方案第七、八章）：
  1. `Photo.isUltraHdr` 只是 `mimeType=="image/jpeg"`，`shouldProbeHdr` 只认它 → AVIF 10-bit / HEIF gain map 永远进不了 HDR 路径；
  2. Glide Downsampler 会把高位深降为 ARGB_8888、采样缩放可能丢 gainmap → 高位深内容必须走 ImageDecoder 直接路径；
  3. `MediaScanner` 扫描期已探测的 `Photo.isHdr` 字段详情页未使用，还在每张 JPEG 重复 200x200 探测（浪费且不一致）。
- 修复方向：HDR 候选条件扩为 `isUltraHdr || isAvif || isHeic`，探测结果按 `hasGainmap || isWideGamut` 判断；优先复用 `photo.isHdr`。
- P1 坑：JXL 16-bit RGBA_F16 大图内存峰值（4096 长边 ≈ 89-134MB，上限建议降至 2048-2560）、ViewPager2 相邻页 colorMode 竞争闪烁、AvifRegionDecoder 严格按 sampleSize 缓存导致缩放反复全图解码。
- 方案文档已更新至 v2（`docs/minsdk35-migration-plan.md`），含解码决策树与 13 条坑点分级清单。

## 方案自评审（v3，同日晚些时候）

对解码展示方案做了批判性复核，文档新增"九、方案自评审"章节，4 项修订：

- **R1**：AvifRegionDecoder 改 ImageDecoder 必须 `setTargetColorSpace(SRGB)`——10-bit AVIF 会被 ImageDecoder 输出为 RGBA_F16（8B/px），tile 解码内存翻倍反而比 HeifCoder 更差；转换到 sRGB 输出 8-bit tile 才不倒退。
- **R2**：`photo.isHdr` 对 AVIF/HEIF 恒为 false（`detectUltraHdr` 仅检 JPEG），"复用扫描期标记"只对 JPEG 生效 → 加详情页探测结果缓存（LruCache）避免滑动重复探测，不扩展扫描器。
- **R3**：HEIF gain map（ISO 21496-1）在 ImageDecoder 上能否 hasGainmap==true 官方未明确背书，需样本实测；不可行则降级 isWideGamut→WIDE。
- **R4**：loadHdrBitmap 需泛化为"原生解码（HDR/WIDE）"，探测三档分流。

评审结论：方案合理、精简（最小必要改动 ~100 行级），可靠性有条件通过，8 项实测验证清单待落地前执行。

## 大图解码链路评估（v4，同日）

用户追问 Glide/子采样对大体积 AVIF/HEIF 的限制与更先进方案。核实到关键事实：

- **`BitmapRegionDecoder` 的 AVIF 区域解码是 2025-09-17 才合入 Skia**（commit "BitmapRegionDecoder: Enable AVIF support"，Bug 435430895），对应 Android 16（API 36）+。**minSdk 35 下 AVIF 无原生 tile 解码，自定义 AvifRegionDecoder 必须保留**（平台边界）。
- HEIF 的 BitmapRegionDecoder 支持更早（Skia kHEIF）→ HEIF 大图可走 ZoomImage 内置原生子采样，不需要 avif-coder；内置失败再注册 AvifRegionDecoder 兜底。
- 限制诊断：Glide 8-bit 降级/2 幂采样/无 F16 池（只适合列表预览）；自定义解码器整帧解码+裁切、缩放频繁全图重解。
- 先进方案分层：A（本次内）：HEIF 原生子采样 + AvifRegionDecoder v2（SRGB tile + 多级采样缓存 512/1024/2048 + 容差）+ 渐进加载（缩略图→2K→全图）+ 原生硬件加速（HEVC/AV1）；B（后续）：多分辨率金字塔磁盘缓存 + FileChannel.map；C：HEICS/AVIF 序列用 MediaCodec；D：HDR 展示平台最优链路 = ImageDecoder + colorMode + headroom。
- 方案文档更新至 v4（新增第十章）。

## 技术选型定稿（v5，同日）

用户最终需求：JXL 单独处理（由我定方案）；AVIF/HEIF 原生 + HDR 展示 + 子采样；现有栈不行就找替代库。

核实与定稿（文档新增第十一章）：

- **ZoomImage README 无内置 AVIF 区域解码**；Glide/Coil/Fresco/libavif 均无 AVIF region/tile 解码 API（AV1 帧内编码格式本质），Google Photos 也是整帧解码 + 多分辨率缓存 → **不需要换库**。
- 需求满足矩阵：HEIF 三项全原生（BitmapRegionDecoder 子采样 + ImageDecoder HDR）；AVIF 原生解码/HDR ✅，子采样 ⚠️ 自定义（API 36+ 才原生，平台边界）。
- **JXL 定稿**：识别用 Photo.isJxl（MIME+扩展名）；缩略图 ThumbnailManager 走 jxl-coder 核心库生成 512px 落盘；Glide 兜底走 jxl-coder-glide；详情页 loadJxlDirect（DEFAULT 自动 8/16-bit）；16-bit 解码上限 2560（防 F16 OOM）；无 EXIF、无子采样为已知限制。
- 最终技术栈：Glide 5 + ZoomImage 1.6 + ImageDecoder/BitmapFactory 原生（AVIF/HEIF）+ jxl-coder（JXL）+ AvifRegionDecoder v2（重写）；移除 avif-coder。

## 高位深 10/12-bit 评估（v6，同日）

用户要求支持 10/12-bit AVIF/HEIF。评估结论（文档新增第十二章）：

- **10-bit ✅ 全原生**：解码（AVIF API 34+ 强制 / HEIF Main10 API 28+）+ RGBA_F16 + HDR/WIDE colorMode 显示；HEIF gain map（21496-1）API 35 待实测（R3）。
- **新增修订 R5**：colorModeForBitmap 需恢复 PQ/HLG transfer 检测——BT2020_PQ/BT2020_HLG 应走 COLOR_MODE_HDR 而非 WIDE（仅 isWideGamut 会误判为广色域 SDR）。项目 AGENTS.md 三重检测正是为此，v3 简化时勿丢。
- **12-bit ❌ 不支持**，三层理由：①官方 AVIF 只保证 baseline（12-bit 解码不保证，Oppo 定制 ROM 佐证）；②Android 位图高位深只有 RGBA_F16，无 12-bit 格式；③无 12-bit 显示面板（消费级最高 10-bit，8-bit+FRC 为主）。12-bit 文件正确做法=降级显示，不引入兜底库。
